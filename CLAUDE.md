# CLAUDE.md — методология pm-admin

## TL;DR

- **Vue 3 + TypeScript** (строгая типизация).
- `<script setup lang="ts">`.
- **Типизация всего**: `props`, `emits`, `ref`, `computed`, функции.
- **Архитектура**: Ядро на TS + Событийная модель (Parent-Child).
  - Родитель подписывается на события ребёнка.
  - Родитель может вызывать методы ребёнка (через `ref`/`expose`).
  - **Никаких горизонтальных связей**. Всё через родителя.
  - Barrel-экспорты (`index.ts`).
- **UI**: `tir-components` + `tir-style-system` из verdaccio.
- **API**: Вызывается только в сервисах, не в компонентах Vue напрямую. Адаптеры обязательны.
- **Composables**: Не обязательны (использовать по необходимости).
- **Состояние**: `AppAdminState` (агрегатор) + локальные стейты модулей и `ref`/`reactive`.
- **Язык**: Ответы и коммиты на **русском**.
- **Коммуникация**: Если есть неоднозначности — **задавай вопросы**. Предлагай лучшие варианты.

## Правила кода

### TypeScript & Vue
- `<script setup lang="ts">`.
- **Props**: интерфейсы, `defineProps<Props>()`.
- **Emits**: `defineEmits<{ ... }>()`.
- **Refs/Computed**: типизируем явно, если не очевидно из инициализации (например, `ref<string | null>(null)`).

### Стиль
- Одинарные кавычки (`'`).
- Отступы: 2 пробела.
- Имена компонентов: `PascalCase`.
- Имена файлов компонентов: `PascalCase`.
- Имена папок: `kebab-case`.
- Barrel-экспорты: `index.ts` в каждой папке-модуле.

## Работа с данными

1. **API Layer**: `src/api` (автоген через `data-source-builder`).
2. **Service Layer**: классы-сервисы, только они вызывают API.
3. **Adapter Layer**: DTO ↔ UI, обязательно.
4. **State Layer**: `AppAdminState` (глобальный агрегатор) или локальный стейт модуля/компонента.
5. **UI Layer**: «глупые» компоненты. Данные — через `props`, наружу — через `emits`.
6. **Widgets**: автономные компоненты со своим API и стейтом, не зависят от других модулей. Могут использоваться где угодно.
7. **Domain Layer**: бизнес-логика в подмодулях (`app-auth`, `app-employees`, …).
8. **Взаимодействие между модулями**: только через родителя (`AppAdminService`), который имеет доступ ко всему стейту. У каждого модуля свой `Service` и `State`. `State` модуля входит в глобальный `State`, `Service` — нет. Если нужно дотянуться до другого модуля, это делает родительский `Service` (или ближайший общий предок по иерархии сервисов).
9. **Автономность модулей**: максимально автономны. Свой сервис, свой стейт, свои компоненты. Зависимость на другой модуль — только через родителя.

## UI/UX

- Компоненты небольшие и фокусированные.
- Поддержка `v-model` для инпутов.
- Состояние инпутов (focus/blur) — управляемое.
- Все стили через `tir-style-system`, никаких хардкод-цветов.

---

## Тестирование

- Юнит-тесты для сервисов и адаптеров обязательны, когда появляется бизнес-логика.
- Компоненты — точечно, где это осмысленно (таблицы, формы с валидацией).
